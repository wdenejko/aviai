01 — Executive summary

A decisive, clean win — and an honest ceiling

The base model reads METARs well but can't do the arithmetic a decode needs (inHg→hPa, m·s⁻¹→kt, SM→m) and fabricates absent fields. One epoch of LoRA installs the conversion habit and the "use null" discipline at once. The lift is large and paired-significant.

  • Value accuracy 69.5% → 92.9% (+23.5 pts). McNemar on paired per-field correctness: 1,437 fixes vs. 3 regressions, p ≈ 4.6×10⁻³¹² — near-zero collateral damage.
  • Hallucination 31.0% → 0.8%. The safety axis, essentially closed — the finetune learned to emit null instead of inventing a value.
  • Whole-record exact match 2.4% → 38.2% (16×; 223 records fixed, 1 regressed). 38% of reports are now decoded perfectly, all 11 fields.
  • The improvement is uniform across difficulty — clean +24.2, dissent +23.4, parse_fail +20.6 — so it's a genuine skill, not overfit to easy records.
The ceiling Every reference in eval/v1 comes from the parser consensus + NOAA gold. By construction this is a fidelity test, not a superiority test: the LLM's ceiling is the parser (~99.9%). The finetune reaches 92.9% fidelity to that oracle — it approaches the parser, it never exceeds it. Demonstrating LLM > parser needs a different eval (§6).

03 — What the finetune fixed

Conversions the base could not do at all

The base model's errors concentrated in two places: it never converted units, and it fabricated a wind_gust when none was reported (167 of its 220 hallucinations — 76% — were invented gusts). The finetune addresses both directly, because the SFT targets carry the correct conversions and correct nulls.

KSEA … A2994 …   inHg→hPa   base null / 29.94   →  finetuned 1014 ✓
UUWW … 16005MPS …  m·s⁻¹→kt   base null / 16      →  finetuned 10 ✓
… 10SM …          SM→metres  base 10           →  finetuned 16100 ✓
… (no gust group)  wind_gust  base fabricated    →  finetuned null ✓
The nuance LoRA installs the conversion behaviour — the model now attempts every conversion, where before it did none. Precision is capped by model size: a 2B model does the multiply approximately, so A2979 can still land on 1014 instead of 1009. It's a faithful approximate converter, which is exactly why value accuracy climbs to 93% but whole-record EM stops at 38%.
04 — The serving bug that hid the win

Template drift: minja vs. HF

The first finetuned eval scored only 73.5% JSON-valid — the model emitted the turn delimiter <|turn>model as literal text instead of JSON, on 164 of 620 records. It was not a model failure. Gemma-4's chat template is a large tool-calling template; at serve time llama.cpp renders it with its own engine (minja), which diverges subtly from how HF Transformers rendered the same template at training. A base model tolerates the drift; a hard-finetuned model (train loss 0.06) overfits to the exact training prompt and falls off distribution.

Fed the exact training-format prompt via the raw /completion endpoint, every broken record produced clean JSON (stop=eos). The harness gained a --completion path that reproduces the training wrapper byte-for-byte, sidestepping the server's template engine.

Lesson: a before/after must never cross serving stacks — and for a hard-finetuned model, "same template, different engine" is a different stack. Serve == train, byte for byte.

05 — Is it viable?

Works decisively; usefulness is a separate question

Two honest headlines sit side by side. The finetune works — large, uniform, paired-significant. And this eval cannot tell us if the model is useful, only that it faithfully mimics the parser that defines its ground truth. As a production METAR decoder the LLM is not viable — a 200-line parser does clean decode at ~99.9%, instantly, with zero hallucination. As a learning vehicle this is close to ideal: formal grammar means perfect ground truth, a crisp measurable skill, and a textbook before/after.

The genuinely interesting frontier — where an LLM could beat a parser — is non-conforming input the automated decoders get wrong, validated against independent human gold. That data does not exist in eval/v1 and is the next investment worth making.

06 — Training & reproducibility

The recipe

  • Base: unsloth/gemma-4-E2B-it (5.15B params, Dense+PLE). Unsloth 2026.7.6 has native Fast Gemma4 patching — FastLanguageModel loads the PLE arch directly.
  • Adapter: bf16 LoRA, r=16, α=32, dropout 0, on q/k/v/o/gate/up/down_proj → 25.3M trainable (0.49%). Adapters attach to the language tower only.
  • Data: 3,000 conversion-heavy pairs from the disjoint train split (held-out stations excluded, before the time boundary). Targets are gold-validated consensus decodes.
  • Schedule: lr 2×10⁻⁴, batch 8 × grad-accum 2, 1 epoch = 188 steps. Loss 1.73 → 0.15. ~34 min on dashi's Radeon 8060S (gfx1151, ROCm 7.2, ~10.5 s/step).
  • Deploy: LoRA → GGUF (convert_lora_to_gguf.py, 50.7 MB) → served as base Q8 + adapter on llama.cpp, evaluated via --completion.
Context This is the study's first result on real Gemma-4. Earlier sessions conflated Gemma-4 (released 2026-04-02, after the assistant's knowledge cutoff) with Gemma-3n and unknowingly measured gemma-3n under a gemma-4 label. All that work is archived under reports/gemma-3/; the redo starts here.
